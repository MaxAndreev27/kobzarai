# Перевірка українського чат-персонажа

Набір `chat_uk.jsonl` призначений для ручного порівняння базових моделей,
промптів, пошуку та адаптерів. Він не є навчальним датасетом і не містить
еталонних відповідей. Завдання і критерії мають бути переглянуті людиною:
наявність питання про твір чи біографію сама по собі не підтверджує відповіді.

## Формат

Кожен рядок — окремий JSON-об'єкт:

- `id` — незмінний ідентифікатор завдання.
- `category` — група перевірки.
- `split` — `development` для налаштування або `holdout` для фінального порівняння.
- `messages` — готова історія у порядку надсилання, останнє повідомлення завжди
  належить користувачу. Попередні відповіді асистента задані для однакового
  контексту і не є результатами роботи моделі.
- `checks` — специфічні для завдання критерії ручної перевірки.
- `source_ids` — необов'язкові ID записів у `data/processed/poems_uk.jsonl`,
  які можуть допомогти перевірити відповідь про твір. Сам ID не є відповіддю.

Є 40 завдань: по п'ять у восьми категоріях; у кожній категорії три
`development` і два `holdout`. Не використовувати `holdout` для добору
промпта, моделей, параметрів, RAG чи навчання. Якщо результати `holdout`
використані для налаштування, він більше не є незалежним: потрібен новий набір.

## Запуск локальної базової моделі

За наявності запущеного локального Ollama і завантаженої `qwen3:1.7b`:

```sh
cd ml
uv run python evaluation/run_ollama.py --output outputs/qwen3-1.7b-dev.jsonl
```

Скрипт запускає лише `development`, без пошуку, за замовчуванням на CPU.
Додайте `--device gpu`, щоб Ollama автоматично вибрав GPU; після кожної
відповіді скрипт зберігає розміщення моделі з `/api/ps` і зупиняється, якщо
використання GPU не підтверджено. Це підтверджує використання GPU-пам'яті,
але не визначає бекенд (Vulkan чи ROCm) і не гарантує повне розміщення на GPU.
Для короткої перевірки можна додати `--limit 1`; для іншої локальної моделі — `--model`.
Результат містить конфігурацію, хеш набору, історії запитів і повні відповіді
Ollama. Існуючий файл не перезаписується. Помилка запиту записується у файл,
а запуск зупиняється з ненульовим кодом. Відповіді, обірвані лімітом токенів,
можна визначити за полем `response.done_reason`.

Для пошукового експерименту додайте `--rag`. Повторюваний параметр `--case-id`
обирає завдання `development`, наприклад:

```sh
uv run python evaluation/run_ollama.py --device gpu --rag \
  --case-id works-01 --case-id works-02 --case-id works-03 \
  --output outputs/rag-works.jsonl
```

Спочатку виконується пошук твору за назвою, потім — лексичний BM25-подібний
пошук у його фрагментах (до 800 символів, перекриття 160 символів). До
запиту додаються два найкращі фрагменти з назвою, посиланням і зміщенням у
тексті. Відмінені форми знайденої однослівної назви не впливають на
ранжування. Для явного запиту про початок твору перший фрагмент має
пріоритет, навіть якщо ключових слів у ньому немає; фрагмент при цьому не
обов'язково містить відповідь. Цей евристичний пріоритет не застосовується
до згадок розділу, частини, кінця або заперечення початку; він не визначає
структуру твору. Показник `score` включає позиційний бонус і не є
ймовірністю релевантності. `source_ids` завдання не використовуються як підказка. Це не
семантичний пошук: синоніми та запити, що не містять слів із потрібного
фрагмента, можуть не знайти релевантний текст. Підтримка відмінків
обмежена; для «Причинна» додано окремі прикметникові форми, зокрема
«Причинній» та «Причинної». Назва в лапках має збігатися повністю, а явно вказана невідома
назва після слів «твір», «поема» тощо не замінюється випадковим збігом з
іншого місця запиту. Без явної назви звичайні слова все ще можуть збігтися
з назвами творів; цей режим не шукає цитати за всім корпусом.
Невідомі чи неоднозначні назви та відсутність релевантних фрагментів
позначаються окремим статусом у результаті.

Набір `retrieval_cases.jsonl` містить вісім перевірок знаходження відомих
цитатних фрагментів у локальному корпусі. Додатковий набір
`retrieval_end_to_end_cases.jsonl` перевіряє форми назв, перефразування,
невідомі та неоднозначні назви, а `retrieval_ranking_cases.jsonl` —
фрагменти з різних частин творів. Усі набори — development, не незалежний
holdout; вісім початкових питань використовувалися під час налаштування.
Для відтворюваного наскрізного вимірювання:

```sh
uv run python evaluation/evaluate_retrieval.py \
  --output outputs/retrieval-end-to-end.json
```

Для кожного запиту скрипт спочатку знаходить твір за текстом запиту і лише
потім шукає фрагменти в отриманому творі. Еталонний `work_id` і `evidence`
використовуються тільки для перевірки, а не для пошуку. Звіт містить хеші
наборів і корпусу, статуси, ID та зміщення, кількість правильно знайдених
творів і кількість запитів із повним еталонним фрагментом у top-1/top-2.
Для невідомих і неоднозначних назв окремо рахується правильність статусу.
`not_found` не доводить, що твір не існує. Ці метрики не оцінюють якість
згенерованої відповіді і не доводять, що інші фрагменти є нерелевантними.

Перевірити тести й runner можна командами:

```sh
uv run ruff check evaluation
uv run python -m unittest discover -s evaluation -p 'test_*.py'
```

Для відтворення зберігається SHA-256 фактично завантаженого корпусу. Тексти
не є джерелом біографічних фактів. Результати із пошуком потребують такої ж
ручної перевірки, як і результати без нього.

## Експериментальний пошук за цитатою

Окремий opt-in режим `--rag --quote-search` шукає цитату в усіх записах
корпусу, а не назву в запиті. Типовий пошук за назвою та гібридний пошук
не змінено; режим не підключений автоматично до них або до backend.
Він очікує рівно одну цитату в лапках `«…»`, `“…”` або `"…"`, щонайменше
з чотирьох слів. Апостроф усередині слова враховується при підрахунку слів.
Порівнюються послідовності цілих слів без урахування регістру, пробілів і
пунктуації; помилки та перефразування не виправляються. Дві пари лапок,
навіть якщо одна містить назву твору, дають `multiple_quotes`.

Якщо цитату знайдено лише в одному записі й хоча б один чанк містить її
повністю, повертається `matched` і до двох таких чанків. `score=1.0`
позначає нормалізований збіг, а не ймовірність чи семантичну релевантність.
Одна цитата в кількох чанках одного запису не є неоднозначністю; збіг у
кількох записах дає `ambiguous`, навіть якщо це дублікати одного твору.
Для `no_quote`, `multiple_quotes`, `quote_too_short`, `not_found`,
`ambiguous` та `no_relevant_chunk` runner записує відмову без генерації.
`not_found` не доводить, що цитата не існує; `no_relevant_chunk` означає,
що повний запис містить цитату, але жоден доступний чанк не містить її повністю.

Порівняння з title-only baseline на вузькому development-наборі:

```sh
uv run python evaluation/evaluate_quote_retrieval.py \
  --output outputs/quote-retrieval-dev.json
```

На `retrieval_quote_cases.jsonl` пошук за цитатою повернув правильний запис
і цитату на першому місці у 10/10 позитивних випадках та правильний статус у
6/6 негативних або неоднозначних; title-only baseline знайшов цитату на
першому місці у 0/10 позитивних. Це спеціально підготовлений development-набір,
а не незалежний holdout чи оцінка якості відповідей моделі.

Перевірка відповідей локальної моделі на окремих development-прикладах:

```sh
uv run python evaluation/run_ollama.py --model qwen3:8b --device gpu \
  --rag --quote-search --dataset evaluation/retrieval_quote_chat_cases.jsonl \
  --output outputs/qwen3-quote-chat.jsonl
```

`--dataset` дозволяє вибрати JSONL із тим самим форматом завдань; runner
використовує тільки `development` і записує хеш фактично завантаженого набору.
Для знайденої цитати runner окремо передає моделі назву з метаданих і
просить стислу відповідь без непідтверджених фактів. У першому прогоні 8B
модель включила слово «символи» до назви, помилково назвала «Кобзар» поемою,
а одну відповідь обірвав ліміт токенів. Після уточнення промпта на тих самих
п'яти прикладах три назви були правильними, два запити отримали детерміновану
відмову і всі три генерації завершились `stop`. Це налаштування на
development-даних, не незалежне підтвердження достовірності моделі.
Знайдений фрагмент і назва не гарантують правильної інтерпретації чи
атрибуції; результати потребують перевірки.

## Порівняння лексичного й семантичного пошуку

`retrieval_semantic_cases.jsonl` — окремі, заздалегідь підготовлені
development-запитання, включно з двома без відповіді в зазначеному творі.
Це не фінальний holdout. За запущеного Ollama та локально завантаженої
[BGE-M3](https://ollama.com/library/bge-m3):

```sh
ollama pull bge-m3
uv run python evaluation/compare_retrieval.py \
  --output outputs/semantic-comparison.json
```

Обидва методи використовують той самий автоматичний пошук назви й ті самі
чанки; еталонні ID використовуються лише для перевірки. Порівнюються
наявність вказаного фрагмента у top-1/top-2, час запиту і кількість
повернутих кандидатів для запитань без відповіді. Список еталонних
фрагментів не є повним переліком можливих правильних доказів. Лексичний
метод включає евристику початку твору; dense-метод використовує косинусну
близькість без цієї евристики або порога релевантності. Жоден метод не
гарантує, що повернутий фрагмент містить відповідь.

Скрипт індексує лише твори, знайдені за назвами запитів, не весь корпус.
Індексація й dense-запити виконуються локально через Ollama з перевіркою
GPU-пам'яті після кожного запиту; CPU-версія лексичного пошуку не потребує
індексації. Час dense-запиту включає запит до Ollama і перевірку GPU,
а час індексації — створення векторів і перевірку розміщення, тому їх слід
розглядати як окремі витрати. Дані й хеші корпусу, модель, фактичне
розміщення та індивідуальні результати зберігаються у звіті. Тексти не
надсилаються до хмарного API. Наявний файл звіту не перезаписується.

## Експеримент із гібридним пошуком і відмовою

```sh
uv run python evaluation/evaluate_hybrid.py \
  --output outputs/hybrid-abstention.json
```

Скрипт об'єднує повні лексичний та BGE-M3 рейтинги за reciprocal rank fusion
(k=60), після чого обирає два фрагменти. Евристична оцінка достатності —
найбільша косинусна близькість запиту серед цих двох фрагментів. Поріг
добирається за balanced accuracy на `retrieval_semantic_cases.jsonl` і
фіксується перед оцінюванням `retrieval_hybrid_validation_cases.jsonl`.
За однакового результату обирається вищий поріг. Нерозпізнана або
неоднозначна назва також призводить до відмови.

Це лише симуляція рішення пошуку: скрипт не запускає LLM і не змінює
основний runner. Поріг навчався лише на двох запитаннях без відповіді,
тому не є надійною оцінкою достатності доказів. Висока схожість не гарантує,
що знайдені фрагменти відповідають на питання. У звіті окремо наведено
пропуски знайдених еталонів, відхилені питання з відповіддю та прийняті
питання без відповіді. Еталонний уривок не обов'язково є єдиним можливим
доказом. Новий набір після цього експерименту також є development, а не
незалежним фінальним holdout.

### Реальні відповіді 8B на тих самих фрагментах

За наявності попереднього звіту й локальної `qwen3:8b`:

```sh
uv run python evaluation/run_hybrid_answers.py \
  --hybrid-report outputs/hybrid-abstention.json \
  --output outputs/qwen3-8b-hybrid-gate.jsonl
```

Скрипт перевіряє хеші корпусу й набору, відповідність запитів та пошуку назв,
відновлює збережені чанки за ID і межами та перевіряє рішення порога. Еталонні
відповіді в запит моделі не передаються. Для кожного кейсу генерується одна
відповідь без порога; у парному порівнянні прийняті порогом відповіді ті самі,
а відхилені замінюються фіксованою відмовою. Окремо `source_guard_answer`
містить відповідь моделі, якщо є фрагменти, або фіксовану відмову з проханням
уточнити назву, якщо фрагментів немає. Для неоднозначної назви відмова окремо
згадує неоднозначність. Це симуляція після генерації, а не правило основного
chat runner; вона не використовує поріг і не перевіряє достатність знайденого
фрагмента. Зберігаються повний запит,
відповідь Ollama, параметри, digest, хеші та розміщення з `/api/ps` після
кожної генерації. Помилки записуються, наявний файл не перезаписується.
Використання GPU-пам'яті не визначає бекенд. Перевірка числа токенів
відхиляє запити біля межі контексту, але сама не доводить відсутність
автоматичного скорочення в Ollama.
Якщо змінився пошук назв, старий звіт може більше не пройти перевірку
відповідності: для нового запуску спочатку створіть новий звіт
`evaluate_hybrid.py`; для відтворення старого використовуйте відповідну
версію коду. Старі результати при цьому не перезаписуються.

Для порівняння інструкцій додайте `--prompt quote` (відповідь із короткою
цитатою) або `--prompt direct` (спочатку перевірити наявність конкретного
факту). За замовчуванням — `--prompt baseline`. Назва варіанта й повний
системний промпт зберігаються у результаті. Усі варіанти експериментальні;
вони не змінюють основний chat runner.

Ручний розбір одного локального запуску (`qwen3:8b`, Q4, seed 42, Ollama
0.40.18, 4096 токенів контексту, до 160 токенів відповіді) на тих самих
18 development-кейсах:

| Група | Без порога | З порогом |
|---|---|---|
| 10 запитань із відповіддю в творі | 5 правильних; 3 часткові/з непідтвердженими деталями; 1 повз питання; 1 відмова з хибним твердженням | 5 правильних; 1 часткова; 4 відмови |
| 6 запитань без відповіді в творі | 5 зазначили недостатність; 1 заявила, що номера телефону немає в усьому вірші, чого самі фрагменти не доводять | 6 фіксованих відмов |
| 2 запитання з невідомою або неоднозначною назвою | 1 коректна відмова; 1 відмова із надто категоричним твердженням про відсутність твору в корпусі | 2 фіксовані відмови |

У часткових відповідях модель приписала козакові епітет «чорнобривий»,
який у фрагменті стосується дівчини; дала граматично неоднозначну фразу про
козака; а також додала непідтверджене припущення про Настю. Для «Заповіту»
вона переказала інші рядки замість відповіді, хоча потрібний уривок був
переданий. Для відміненої «Причинній» пошук не знайшов назву, а модель
необґрунтовано заперечила наявність опису річки й вітру в самому творі.
Усі 18 генерацій завершились із `done_reason=stop`, GPU-пам'ять підтверджено
після кожної. Оцінки — ручні та чутливі до формулювань; один запуск і малий
development-набір не встановлюють надійність або статистичну перевагу порога.
Не використовувати цей поріг у production без ширшої незалежної перевірки.

Після виправлення «Причинній» гібридний пошук на тому самому наборі знайшов
еталонний уривок у top-2 для 7/10, раніше було 6/10; у виправленому запиті
уривок став першим. Лексичний пошук окремо не повернув жодного фрагмента
для цього запиту. Поріг не змінився і все одно відхилив запит, попри наявність
еталона. Збережені top-2 фрагменти та їхні оцінки для інших 17 запитів не
змінилися.

Два нових прогони 8B з додатковою інструкцією не робити висновків про цілий
твір чи корпус дали змішані результати: попри надані рядки про Дніпро модель
заперечила наявність конкретного опису; для запитання про номер телефону
знову зробила висновок про весь твір лише з фрагментів. Для неоднозначної
назви модель в одному прогоні також безпідставно заявила про відсутність
фрагмента в корпусі. Отже, посилення prompt не гарантує достовірності.
У симуляції `source_guard_answer` два запити без джерел отримали
детерміновану відмову, решта 16 зберегли відповіді моделі, включно з
помилками. Ця перевірка підміняє відповідь, коли немає джерела, але не
захищає від помилок із нерелевантним чи навіть правильним джерелом. Обидва
прогони використовували seed 42, однак деякі формулювання відповідей
відрізнялися; це development-спостереження, не незалежний тест.

### Порівняння інструкцій за однакових джерел

Один запуск кожного варіанта на тому самому наборі з 18 запитань. Модель,
digest, seed, параметри, звіт гібридного пошуку і текст користувацьких
повідомлень однакові; оцінювалися **відповіді моделі без порога та підміни
`source_guard`**. Повними вважали відповіді, які передавали ключовий зміст
без непідтверджених деталей; часткові, помилкові та відмови не зараховували.

| Інструкція | Повні відповіді на 10 запитань із відповіддю в творі | Коректна недостатність даних на 6 запитаннях без відповіді |
|---|---:|---:|
| `baseline` | 5 | 5 |
| `quote` | 7 | 2 |
| `direct` | 3 | 6 |

`quote` виправив відповідь про те, кого покохала дівчина, і про згадку в
«Заповіті», але на чотирьох із шести запитань без відповіді зробив
непідтверджені твердження: зокрема вигадав назву села в «Катерині» та
неточно процитував фрагмент. В іншому випадку процитував справжні, але
нерелевантні рядки як нібито доказ. Із дев'яти цитат у десяти відповідях
про твори лише три повністю збігалися зі знайденими фрагментами після
нормалізації пробілів; в одному випадку модель навела рядки без лапок.
Точний збіг також сам по собі не доводить, що цитата відповідає на питання.

`direct` правильно відмовив на всіх шести запитаннях без відповіді, але
відмовив і на п'яти з десяти запитань із відповіддю в творі, зокрема коли
потрібні рядки були надані. На одному з решти питань додав непідтверджене
твердження, а ще на одному дав неповну відповідь. Обидві інструкції
коректно зазначили нестачу даних у двох запитаннях без джерел.
Усі 36 генерацій завершились із `done_reason=stop`; використання GPU-пам'яті
перевірено після кожної. Один seed і вже використаний development-набір не
доводять перевагу жодного варіанта; жоден не обрано для production.

### Експеримент із вибором рядків перед відповіддю

`retrieval_evidence_dev_cases.jsonl` — новий development-набір: 12 питань з
еталонним уривком, шість без відповіді в зазначеному творі та два з
невідомою або неоднозначною назвою. Це не незалежний holdout. Для відтворення
за наявності локальних BGE-M3 та Qwen3 8B:

```sh
uv run python evaluation/evaluate_hybrid.py \
  --validation evaluation/retrieval_evidence_dev_cases.jsonl \
  --output outputs/hybrid-evidence-dev.json
uv run python evaluation/run_hybrid_answers.py \
  --hybrid-report outputs/hybrid-evidence-dev.json \
  --cases evaluation/retrieval_evidence_dev_cases.jsonl \
  --output outputs/evidence-baseline.jsonl
uv run python evaluation/run_evidence_answers.py \
  --hybrid-report outputs/hybrid-evidence-dev.json \
  --cases evaluation/retrieval_evidence_dev_cases.jsonl \
  --baseline outputs/evidence-baseline.jsonl \
  --output outputs/evidence-two-stage.jsonl
```

Для порівняння використовуються ті самі автоматично знайдені фрагменти,
модель, параметри та запитання, але різні системні інструкції. Поріг
схожості не застосовується. В обох варіантах відсутність джерел дає
фіксовану відмову. Базова відповідь повторно береться зі збереженого файлу;
скрипт перевіряє хеші, модель, версію Ollama, конфігурацію, запити та
джерела. На першому етапі модель вибирає номери послідовних рядків у
знайдених фрагментах або відмовляється; на другому відповідає лише за цими
рядками. Фрагмент витягується програмно з точними символьними межами; у
результаті `evidence` — **кандидат**, а не перевірений доказ. Невалідний
вибір, понад шість рядків або обірвана генерація призводять до зафіксованої
відмови. Помилки запитів записуються і зупиняють запуск; усі запити, відповіді,
розміщення GPU та часи етапів зберігаються.

Ручний розбір одного запуску Qwen3 8B, seed 42, Ollama 0.40.18:

| Показник | Базова схема | Два етапи |
|---|---:|---:|
| Повні правильні відповіді на 12 питань із відповіддю у творі | 10 | 9 |
| Коректна недостатність на шість питань без відповіді | 5 | 6 |
| Фіксована відмова для двох проблемних назв | 2 | 2 |

У top-2 було 12/12 еталонних уривків. Із 12 питань з відповіддю перший
етап двоетапної схеми вибрав достатній уривок у 8 випадках; у трьох він
був недостатнім або нерелевантним, ще один вибір перевищив ліміт рядків
і був відхилений. Одна з дев'яти правильних відповідей спиралася на
уривок, який без сусідніх рядків не встановлював, кого саме карає орел.
Усі 17 прийнятих уривків дослівно збігалися з корпусом за збереженими
межами, **але всі шість кандидатів для питань без відповіді були
нерелевантними**; другий етап у цих шести випадках усе ж відмовив.
Один базовий результат робив висновок про весь твір лише з фрагмента.

Для 18 запитів із джерелами медіана серверного часу генерації становила
4,05 с базово і 6,73 с для двох етапів разом, включно з одним випадком без
другого етапу; це не час пошуку, а моделі завантажувалися в різних умовах.
GPU-пам'ять підтверджено після кожного виклику. Це малий development-набір і
один запуск: не можна переносити ці результати на всі запити. Двоступенева
схема не довела переваги та не інтегрована в основний chat runner або backend.

## Як проводити порівняння

1. Зафіксувати модель та її ревізію, формат і квантовку, runtime, пристрій,
   системну інструкцію, chat template, параметри генерації, seed (якщо
   підтримується), максимальну довжину відповіді та контексту.
2. У системній інструкції явно задати українську мову, образ ШІ, натхненний
   Шевченком, і заборону видавати вигадані факти або цитати за достовірні.
   Для порівняння моделей використовувати ту саму інструкцію і, наскільки
   можливо, однакові параметри. Вказати, чи застосовувався пошук.
3. Кожне завдання починати з чистого сеансу. Передавати всю історію `messages`
   у вказаному порядку; оцінювати лише відповідь на останнє повідомлення.
   Зберігати повний запит, отриману відповідь, помилки та конфігурацію запуску.
   Не замінювати задані попередні відповіді результатами іншої моделі.
4. Не видаляти невдалі, порожні чи обірвані відповіді: зафіксувати їх і
   причину, якщо вона відома. Порівнювати також частоту помилок запуску.
5. Окремо оцінити `development`, потім заморозити конфігурацію і один раз
   провести `holdout`. Для стохастичної генерації фіксувати seed; якщо
   порівнюються кілька запусків, використовувати однаковий набір seed та
   записувати кожен результат.

Корпус творів доступний локально, але ігнорується Git. Перед оцінюванням
зафіксувати його версію або SHA-256 і перевірити наявність потрібних ID.
Збіг із корпусом не доводить достовірність біографії або сучасних фактів:
для них потрібні незалежні надійні джерела. Метадані корпусу вилучені
евристично і також потребують перевірки. Якщо перевірити факт неможливо,
не позначати його як правильний.

## Шкала ручної оцінки

Оцінювати кожну застосовну характеристику окремо:

| Оцінка | Значення |
|---|---|
| 2 | Вимога виконана: відповідь правильна та доречна. |
| 1 | Частково виконана: є помітний недолік, але основний намір виконано. |
| 0 | Не виконана, відповідь відсутня або містить істотну помилку. |
| N/A | Характеристика не застосовується до цього завдання або недостатньо даних для перевірки. |

Характеристики:

1. **Мова:** українська мова, зрозумілість і відсутність небажаного переходу
   на іншу мову. Імена або назви іншою мовою самі по собі не є помилкою.
2. **Завдання та діалог:** виконання обмежень із `checks`, доречність відповіді
   і врахування наданої історії.
3. **Стиль:** відповідність запитаному тону; образність доречна, але не
   обов'язкова, особливо коли просять просту прозу.
4. **Достовірність:** фактичні твердження і цитати підтверджені джерелами;
   відсутність вигадок і чесне позначення невизначеності. Використовувати N/A
   для завдань без перевірюваних тверджень або коли джерело недоступне.
5. **Межі образу:** модель не видає себе за історичну особу і не приписує їй
   вигадані переживання чи сучасні погляди. Застосовувати, коли питання це
   перевіряє або відповідь сама робить такі твердження; інакше N/A.

Для кожної відповіді зберігати оцінки, коротке обґрунтування та посилання на
джерела перевірених фактів. Окремо позначати виконання кожного `checks`.
Агрегувати середню оцінку **кожної характеристики** за застосовними
завданнями та вказувати кількість оцінених і N/A; не змішувати N/A з нулями.
Показувати результати за категоріями, частку повністю виконаних `checks` і
частку помилок запуску. Для пропущених чи обірваних відповідей зазначити
причину і не зараховувати їх як успішні. Порівняння різних моделей проводити
на однаковому наборі завдань, не приховуючи часткових результатів.

Це невеликий ручний набір, тому результати — орієнтир для подальших
експериментів, а не статистичне підтвердження якості чи безпеки моделі.
